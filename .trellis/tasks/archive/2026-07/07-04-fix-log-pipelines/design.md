# 调度与实时日志修复设计

## Scope

本次修改只覆盖 Go 运行态、HTTP activity 契约和 Vue dashboard 日志消费逻辑，不改 Python 废弃路径，不重做调度历史数据模型。

## Data Flow

1. `consumer.Consumer` 与调度器相关代码通过 `runtime.Manager.AddLog()` 统一写日志。
2. `AddLog()` 同时完成两件事：
   - 追加到 Web 日志缓冲，供 `/api/activity` 增量读取。
   - 输出到后端控制台，作为服务端统一调试日志。
3. `GET /api/activity` 新增日志过滤参数，只筛选 `logs`，不影响 `events` 与游标返回。
4. 前端实时日志把“是否接收日志”的单开关改成“请求哪些来源 / 级别”的前端状态；查询参数来自该状态，而不是本地先拉全量再丢弃。

## Logging Strategy

日志设计以 Go 运行态为准，不复刻 Python 端历史文本。新的埋点应围绕当前系统里真正有决策价值的节点展开，让用户能看懂“当前发生了什么”，而不是把旧实现的零散打印原封不动搬过来。

## Scheduler Logging Coverage

调度相关日志至少补到以下节点：

- 建立 cron / interval 计划。
- 调度器启动完成。
- 计划任务被触发执行。
- 本轮计划执行结束。
- 下一次执行时间刷新。
- 停止或替换已有调度计划。

这些日志继续复用统一日志模型返回，避免前后端再裂一条平行契约。日志级别沿用现有 `level`，日志来源新增独立字段，避免把“严重性”和“来自哪里”硬塞进同一个枚举里。

## Filter Model

- 级别维度：沿用 `info / warning / error`，必要时兼容 `success`。
- 来源维度：至少区分 `scheduler / runtime / download`。
- activity 查询同时接受两组筛选参数；缺省时表示不过滤，保证兼容性。
- 前端筛选控件只维护用户选择，并把选择原样传给后端；真正的匹配逻辑只在后端实现。

## Compatibility

- `events` 的使用方式保持不变，避免打断当前 `history_update -> invalidate dashboard` 的刷新链路。
- `logs` 的查询参数会扩展，但默认值应保持“不过滤”，避免未升级的调用方因为漏传参数而读不到日志。
- 前端只声明日志来源和级别，后端负责按条件返回日志，避免筛选规则分叉。

## Risks

- 若前端把日志筛选状态直接绑定到 query key，需要确保切换筛选时不会把事件游标回退。
- 若调度日志点补得太少，仍然会出现“调度没记录”的体验；补太多则可能把 500 条缓冲刷爆，所以日志点只放在关键业务节点。

## Rollback Notes

- 若 activity 过滤参数实现引发兼容问题，可先回退到默认全量返回日志，保留控制台打印和调度日志补点。
